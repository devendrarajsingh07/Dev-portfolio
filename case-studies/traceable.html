Traceable Impact / Case study04 — 10

Every number should have a source.

An impact-reporting workflow that turns inconsistent program files into understandable metrics without losing the evidence behind them.

Explore the story View source
Project
Data systems · Nonprofit reporting
Engineering focus
Data lineage, human review, and privacy
Technology
React · TypeScript · FastAPI · PostgreSQL · pandas · D3

The problem

Small nonprofits often have evidence scattered across attendance sheets, donor files, surveys, and exports. Column names disagree, people appear more than once, and missing information can disappear inside a clean-looking total. The challenge is to produce a readable report while preserving the decisions and records that make each number defensible.

The approach

Traceable separates original evidence from interpretation. It preserves uploaded rows, asks a person to confirm column mappings and duplicate decisions, and stores the exact source-record IDs behind a computed metric. A React interface guides the workflow while FastAPI services manage reconciliation, calculations, privacy, and report generation.

  1. Import original files
  2. Confirm column mappings
  3. Review duplicate candidates
  4. Define and compute a metric
  5. Inspect and share its evidence

Key decisions

Preserve evidence instead of rewriting it

Raw uploads and rows remain immutable. Mappings, duplicate decisions, and corrections are recorded separately, with an append-only audit trail and stable source IDs.

The tradeoff. The data model is more involved than editing a single cleaned spreadsheet, but a reported number can retain its history.

Treat automation as a suggestion

Fuzzy mappings, duplicate candidates, and AI-assisted metric formulas require explicit human review. Formula drafts are validated against the confirmed schema and allowed operations before computation.

The tradeoff. Review takes time, so the interface must make uncertain fields and the consequences of a decision easy to inspect.

Show lineage without exposing identity

Reports use pseudonyms, protected identity mappings, and small-group suppression. Shared reports are frozen, pseudonymized snapshots. The D3 sunburst links metrics to contributing source files using record volume rather than mixing incompatible units.

The tradeoff. Privacy controls can hide detail, and a snapshot deliberately does not update when the working report changes.

Where it stands

The repository describes an end-to-end path from CSV, spreadsheet, or JSON ingestion to a source-linked HTML/PDF report. Staff can inspect uncertain matches, review metric evidence, see unresolved gaps, and create a read-only report snapshot.

Current scope

A computed metric is only as complete as the available records and confirmed decisions. Missing dates, unmapped columns, duplicate uncertainty, and exclusions remain visible. No adoption figures or measured time savings are claimed here.

A useful next evaluation would follow nonprofit staff through the complete review workflow and measure whether they can explain a reported number using its attached evidence.
